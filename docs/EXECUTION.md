# Candidate construction and execution evidence

`GitWorkspace` consumes a trusted fetched object database or trusted local fixture. All source revisions are exact 40-character object identities. It reads raw trees/blobs rather than executing repository code. Tree admission refuses unsafe or duplicate paths, symlinks and submodules, and bounds metadata to 100,000 files. `checkout` preserves all regular blobs byte-for-byte, including binary assets, within a 200 MB total source bound. A single raw Git batch writes bounded temporary output to disk and streams files, avoiding one subprocess per file or loading all assets into memory. The legacy `snapshot` remains a strict text-fixture API with 5,000 files, 2 MB per blob and 20 MB total; production context uses `source_slice` instead.

`source_slice(revision, paths, budget=100000)` returns whole UTF-8 text files, prioritizing explicit changed paths then deterministic source siblings in the same package/directory. It does not fetch every blob in a monorepo. Source byte budgets and a 200-file context cap bound returned content; binary/nontext, invalid UTF-8, missing files and files exceeding the remaining budget are omitted. `source_slice_omissions` maps considered paths to reasons, and `source_slice_coverage` records tree/request/selection counts, selected bytes and nearby files excluded by the cap. Context consumers must bind this coverage evidence and apply owner-approved context-path and secret exclusions before model access. A slice is partial retrieval, not a complete repository review.

Candidate construction uses a fresh bare Git object database and index, applies a unified diff to the captured PR head, validates the resulting tree metadata and changed paths/blobs, then imports raw new objects into the fetched object database. It never stages or edits the caller's checkout. Hooks, global/system Git config, replacement objects, external diff, signing and fsmonitor are disabled; raw blob operations never invoke clean/smudge filters. Unrelated binary blobs are preserved unchanged. Changed before/after blobs must be UTF-8 without NUL bytes, each at most 2 MB and together within the repository policy source budget; patch size and changed-file counts are separately bounded. Renames/copies, binary diffs and mode changes are unsupported and fail closed. A Git worktree or model-produced repository is never a publication source.

Canonical commits use author and committer `Sir Patchington <patchington@localhost>`, Unix timestamp `946684800 +0000`, message `Sir Patchington verified candidate\n`, and the exact captured head as their only parent. The immutable Candidate binds the captured snapshot, patch, tree, commit and policy digest. Reconstructing the same candidate produces the same commit and candidate identity.

`ArtifactStore` writes canonical JSON or bounded bytes to SHA-256 paths using an atomic link, reads only regular files without following final-component symlinks and verifies the hash every time. Existing artifacts are never overwritten. This detects alteration; filesystem permissions alone do not make evidence tamper-proof against the host account. Production callers must pass their durable shared artifact store to the verifier. Its default temporary store is for fixtures and lasts only as long as that verifier instance.

`DockerVerifier(image, timeout=120, artifacts=...)` inspects an already provisioned trusted image, records its actual repository digest and image ID, and executes by image ID with pulling disabled. Every check runs against a new original-head source tree and a separate new candidate source tree; no check sees another check's outputs. Container settings are:

- Network `none`, UID/GID 65532, all Linux capabilities dropped, default Docker seccomp and no new privileges.
- Read-only container root and an exact read-only Docker-managed source volume at `/work`; no Git database, credentials, Docker socket, host home, host path or host environment is mounted or forwarded.
- One CPU, 256 MiB memory, zero extra swap, 64 PIDs, 256 open files, no core dumps, no persistent Docker log driver.
- A 64 MiB `noexec,nosuid,nodev` tmpfs at `/tmp`; source and all other root paths remain read-only. Checks must direct generated outputs to `/tmp`.
- Trusted explicit argv only; no shell wrapper. Each run has an owner-specified deadline capped by verifier timeout, bounded combined output, process-group termination on bounds and forced container cleanup.

Source staging creates a unique Docker-managed volume and a constrained staging container that is never started. `docker cp` transfers only the bounded validated source tree into that volume; execution containers mount it read-only. This requires no shared host path and supports a remote daemon through the trusted CLI's `DOCKER_HOST`, `DOCKER_TLS_VERIFY` and `DOCKER_CERT_PATH` configuration. Docker connection settings remain host-side and are never injected into execution containers. Unique explicit container/volume names permit forced cleanup after a killed CLI; cleanup failure invalidates evidence. External source inventory checks compare content, modes, additions and symlinks after each check. Local fixture checks can mutate their own source and are marked failed; production source volume cannot be written at all.

A positive verification requires required checks, at least one required change-specific regression check, actual command execution, candidate exit zero, unchanged source, bounded output/time and no violations. A regression check must exit nonzero on the original head and zero on the candidate. Missing commands, Docker startup failures, recognized zero-test or all-skipped summaries and unavailable checks cannot produce green evidence. Changes to existing or new tests, common runner/build/lock configuration and CI paths are rejected as modified acceptance inputs. Checks are supplied by the repository owner; candidate/model output never controls them. Optional failures conservatively fail the whole verification.

Evidence JSON has exactly `candidate_id`, `checks` (serialized CheckResult objects), `environment` and `violations`. Each result binds original and candidate exit status, output digests, source integrity, timeout/skipping status and failure details. Environment begins `docker:` and records actual image/resource settings. `LocalVerifier(trusted=True, ...)` is explicitly for trusted fixtures, uses `local:trusted-fixture:unsandboxed` evidence and grants no host security boundary. Production publication must reject local evidence.

`patchington.probes.function_probe` freezes an owner-authored Python supervisor and base64 JSON cases into immutable CheckSpec argv. Python `-I -S` prevents candidate working-directory modules or site hooks from entering the parent. Each case executes candidate code in a separate child; the parent validates exactly one bounded JSON result or expected builtin exception, requires child completion, and prints `PATCHINGTON_PROBE_EXECUTED=N/N` only after every case is observed. Missing/extra/malformed output, an early `os._exit(0)`, wrong results, deadlines and excessive output all fail. `delivery_fee_probe()` supplies the demo cases `src.fees.delivery_fee(49/50/51) -> 5/0/0` with `regression=True`. Actual Docker tests reject the early-exit candidate and pass the fixed boundary, and independently verify a text repair while binary assets remain byte-exact. A 5,002-file Git fixture proves context slicing, candidate construction and raw checkout admit repositories above the strict fixture snapshot limit; this is admission/control evidence, not a throughput benchmark. These cases demonstrate observed behavior; candidate code can still intentionally return expected values for known cases, as with ordinary tests.

Limits: Docker shares a host kernel; this is not a virtual-machine isolation claim. No dependency installation or network package resolution occurs during checks; the owner must provision a suitable trusted image with dependencies in advance. Generic argv exit codes do not prove every semantic assertion ran. Known pytest/unittest empty summaries are detected, but a silent or malicious command can lie about test counts; an adversarial source import can terminate a same-process assertion harness early. High-assurance acceptance should assert from an independent owner-controlled process/service boundary. Runtime secrets accidentally committed in source are not automatically identified or removed. Host credentials are never injected into the execution container.

Validation on 2026-10-21 used actual temporary Git repositories and actual Colima Docker containers with `python:3.12-slim`, repository digest `python@sha256:2f17fc044b579bab302c2e8054d3a686e2cb9a83de48e70534b94cd8ebbe06a9`. The independent regression assertion failed the original head (exit 1), passed the candidate (exit 0), and checked nonroot identity, no inherited canary secret, no Docker socket, read-only root and blocked outbound connection. This is local boundary/control evidence, not production scale, dependency coverage or model-quality evidence. No real model API calls were made.
